# Заказы и клиенты

Endpoint map for the orders/customers domain. Auth, base URL, tool flags,
pagination and global conventions live in [`api.md`](api.md).
Mutating = POST/PUT/PATCH/DELETE (all need `--confirm`).

Работа с заказами — один из двух самых частых сценариев в кабинете, и почти
всегда он начинается с выборки: «покажи заказы в таком-то статусе за такой-то
период». Публичный API устроен иначе, чем кабинет, поэтому начните с раздела о
фильтрации.

## Заказы

| Метод | Путь | Описание |
|---|---|---|
| GET | `/v1/orders` | Получение списка заказов (только `page` / `per_page`) |
| GET | `/v1/orders/{id}` | Получение заказа по ID |
| GET | `/v1/orders/{id}/addons` | Получение списка услуг заказа |
| POST | `/v1/orders/{id}/confirm` | Подтверждение заказа |
| POST | `/v1/orders/{id}/cancel` | Отмена заказа |
| POST | `/v1/orders/{id}/delivery/complete` | Полное завершение доставки заказа |

## 🛑 У списка заказов нет фильтров

`GET /v1/orders` принимает **только** `page` и `per_page`. Ни статуса, ни дат,
ни номера, ни клиента, ни суммы. Это главное расхождение между публичным API и
кабинетом, где поиск заказов — самая частая операция.

Отсюда два правила:

1. **Не выдумывайте query-параметр.** `?status=NEW`, `?date_from=…`,
   `?search=…` — таких параметров нет. Опасность в том, что API молча
   игнорирует неизвестный параметр и отвечает `200`: запрос «сработает», вернёт
   **неотфильтрованную** страницу, и отчёт будет неверным без единой ошибки в
   логах. Сверяйтесь с `kit.py describe GET /v1/orders`.
2. **Фильтруйте после полной вычитки.** Прочитайте коллекцию до конца через
   `kit.py list /v1/orders`, отберите нужное по полям `status` и `created_at`
   локально и укажите покрытие. Если покрытие `partial` — так и скажите:
   «нашёл N подходящих среди прочитанных M из total_count», а не «заказов в
   этом статусе N».

```bash
python3 scripts/kit.py describe GET /v1/orders          # убедиться, что фильтров нет
python3 scripts/kit.py list /v1/orders                  # все страницы + покрытие
python3 scripts/kit.py list /v1/orders --format csv \
    --fields order_number,created_at,status,total_final_price > orders.csv
```

`--format csv` пишет строки в stdout, а вердикт о покрытии — в stderr, поэтому
выгрузку можно перенаправить в файл, не потеряв предупреждение о неполноте.

**Имена колонок берите из `describe GET /v1/orders`, а не по памяти.** Номер
заказа — `order_number`; поля `number` у заказа нет. Колонку, которой нет ни у
одного заказа, `list` отклоняет с exit `2` и печатает список доступных полей.
Так и задумано: пустая колонка в готовой выгрузке читается как факт о магазине
(«служба доставки не указана»), а не как опечатка в `--fields`.

**Вложенное — через путь.** Способ доставки, склад и трек лежат не на верхнем
уровне заказа, а внутри `delivery_chunks[]` — у каждого грузоместа свои:

```bash
python3 scripts/kit.py list /v1/orders --format csv \
    --fields 'order_number,status,delivery_chunks[].delivery_info.method,delivery_chunks[].delivery_info.tracking_number' \
    > delivery.csv
```

Кавычки вокруг `--fields` обязательны: `[` и `]` без них шелл принимает за
шаблон имени файла, и в zsh (по умолчанию в macOS) команда не запустится вовсе.

`chunks[]` собирает значение со всех грузомест заказа в одну ячейку через `; `,
`chunks[0]` берёт только первое. Строка в файле всё равно одна на заказ, а не на
грузоместо: заказ, часть которого едет курьером, а часть в пункт выдачи, даст
`COURIER; PICKUP_POINT`.

Что где лежит внутри `delivery_info`:

| Путь | Что это | Значения |
|---|---|---|
| `delivery_chunks[].delivery_info.method` | способ доставки | `COURIER`, `POSTAL_SERVICE`, `PICKUP_POINT`, `SELF_PICK_UP` |
| `delivery_chunks[].delivery_info.courier_delivery_service_type` | служба доставки — заполнена у курьерских грузомест | `YANDEX_DELIVERY`, `CDEK`, `META_SHIP_DALLI`, `META_SHIP_RUSSIAN_POST`, `OZON`, `MERCHANT_SHIP` |
| `delivery_chunks[].delivery_info.pickup_point_delivery_service_type` | то же для пунктов выдачи | те же значения |
| `delivery_chunks[].delivery_info.tracking_number` | трек-номер отправления | строка |
| `delivery_chunks[].delivery_info.warehouse_id` | склад | **идентификатор, а не название** — названия отдельным чтением `/v1/warehouses` |

Служба доставки лежит в двух разных полях, и какое из них заполнено, зависит от
способа. Выгружайте оба и не называйте пустое «службы нет»: у самовывоза её нет
по существу.

### Статусы заказа

Фильтровать локально можно по полю `status`:

`NEW`, `PENDING_PAYMENT`, `ORDER_PLACED`, `WAIT_FOR_CONFIRMATION`,
`CREATING_INITIAL_RECEIPT`, `SETUP_DELIVERY`, `WAIT_FOR_DELIVERY`,
`CANCELLATION_IN_PROGRESS`, `DELIVERY_CANCELLED`, `FULL_REFUND`,
`PARTIAL_REFUND`, `CREATING_FINAL_RECEIPTS`, `DELIVERED`, `CANCELLED`,
`COMPLETED`.

«Требуют внимания продавца» — это `WAIT_FOR_CONFIRMATION`. Полный набор полей
заказа: `kit.py schema Order`.

## Жизненный цикл: переходы и их правила

- **`confirm` не идемпотентен.** Работает только из `WAIT_FOR_CONFIRMATION`;
  повторный вызов для уже подтверждённого заказа возвращает ошибку. Отказ (`409`
  или `400`) — это **не** повод повторить запрос: прочитайте заказ и сообщите
  его фактический статус.
- **`cancel` вернёт `400`**, если текущий статус не допускает отмену. Отмена
  необратима для покупателя — подтверждайте её у пользователя отдельно и
  показывайте номер заказа, а не только UUID.
- **`delivery/complete` терминален** и предназначен для самовывоза и собственной
  доставки магазина, когда автоподтверждения от службы доставки не будет.
  Подтверждайте его отдельно от `confirm` и не вызывайте «заодно»: это разные
  решения продавца.
- **Проверяйте результат чтением.** У всех трёх переходов состояние заказа —
  единственное доказательство. `2xx` без последующего `GET /v1/orders/{id}` не
  делает операцию завершённой.

## Чего в заказах нет

Произвольного редактирования заказа публичный API не даёт. Нет ручек для:
состава заказа (добавить/убрать товар, изменить количество), возвратов и
частичных возвратов, объединения заказов, смены способа доставки, печати
этикеток и накладных, массовых действий над выборкой заказов. Если пользователь
просит такое — скажите прямо, что операции нет в публичном API, и отправьте в
кабинет. Не подменяйте возврат отменой: это разные операции с разными
последствиями для денег покупателя.

## Клиенты

| Метод | Путь | Описание |
|---|---|---|
| GET | `/v1/customers` | Получение списка клиентов |
| GET | `/v1/customers/{customer_id}` | Получение клиента по ID |
| PATCH | `/v1/customers/{customer_id}` | Обновление клиента |
| GET | `/v1/customers/{customer_id}/orders` | Получение списка заказов по ID клиента |

`GET /v1/customers/{id}/orders` возвращает **только идентификаторы** заказов
(`OrderIDCollection`), без сумм и статусов. Чтобы ответить «на сколько он
купил», нужно дочитать сами заказы через `GET /v1/orders/{id}`. Не считайте
длину списка id ответом на вопрос о деньгах.
