# API contract

The client is fixed to the routes below. Two backends:

* **Core experimental API** under `/api/experimental/v1` — store-scoped Bearer token (`KIT_API_BASE_URL` / `--base-url`).
* **Storefront BFF** under `/constructor-api` — no authentication (`KIT_BFF_BASE_URL` / `--bff-url`, set to the store's storefront origin). Derivation from the Core API URL works only when both share a host; on production the Core API is a separate gateway, so take the origin from the store: the `b2c_url` reported by `scripts/kit.py store` of the `yandex-kit-cabinet` skill (this skill has no such command), or, without that skill, the address the user's customers open. Take that value as-is: a store on its own domain has a `b2c_url` that cannot be assembled from its slug. When neither is set and derivation fails the client refuses with instructions; it never guesses silently.

Compact template-list records include `id`, `title`, `json_schema_bytes`, `alias` (null when absent), and `script_bytes` when the server sends `script`. `templates show` adds the exact `json_schema` string. Aliases are optional and non-unique; UUID is the only identity key.

Section status (`published`/`hidden`) is part of every section in the read shape. A hidden section keeps its settings and is not rendered on the storefront. The projections report it as read, `null` when a response carries none. `section status --id X --status hidden|published [--page ALIAS | --page-id UUID]` changes it in the workspace — on every copy, or on the copy of one page, since status is stored per copy. `hidden` is accepted by the server only for `YandexKit.AnnouncementBar`, `BannersCarousel`, `EmailSubscription`, `Faq`, `FeaturedBlogs`, `FeaturedCollections`, `FeaturedProducts`, `ImageWithText`, `LoyaltyProgram`, `Mystique` and `RichText`; any other hidden section fails the whole write with 400, so the command refuses it and so does a push gate. The diff and the plan list every changed copy under `section_status_changed`; a copy whose status alone changes appears only there, and a section in `sections_changed` that also changes status carries `status_changed` (`before`, `after`). Other edits carry the status through unchanged, and a section added by `section add` is written as `published`.

Template records carry `script` (a string, `""` for a template without JS). Every template response validator tolerates unknown extra fields: a strict check would turn a new response field into a client error after a successful create, and the retry that follows duplicates the template.

Timestamps are parsed as RFC-3339 with 1-9 fractional digits and either `Z` or a numeric offset; the fraction is truncated to microseconds and every instant is normalized to UTC before sorting or `--since` comparison.

## BFF schema engine

| Client command | Method and path | Notes |
|---|---|---|
| `schema fetch [--force]` | `GET /constructor-api/schema` | ETag-conditional; cached under `~/.yandex-kit-skills/cache` (override `KIT_SCHEMA_CACHE_DIR`) |
| `schema widgets` | — (cache) | widget names, ref, field count, `has_version_field` |
| `schema widget --name W [--skeleton]` | — (cache) | compact resolved schema (defaults, enum, editor `options` labels, titles); `--skeleton` builds a locally validated settings object from defaults |
| `schema theme` | — (cache) | compact `globalSettings` schema |
| `schema widget-version --name W` | `POST /constructor-api/migrate` | body is strictly `{"sections":[{"key":"version-probe","widget":W,"settings":{}}]}`; only `settings.version` is read from the response |

The local validator implements exactly the draft-07 subset present in the live document: `$ref` (`#/definitions/...`), `type`, `properties`, `required`, `items`, `enum`, `const`, `minimum`, `maximum`, `anyOf`, `not`, `additionalProperties`. A document using any other constraint keyword (`oneOf`, `allOf`, `if/then/else`, `patternProperties`) is rejected outright rather than checked partially.

Keywords written next to a `$ref` are the editor's own: `{"$ref": "#/definitions/CompanyLogoSize", "default": "md"}` has default `md` although the referenced enum starts at `xs`, and a definition may itself be a `$ref` plus `default` (the vertical section padding defaults to `single` that way). Skeletons and projections merge those siblings into the resolved node, the one closest to the property winning; a sibling default that does not validate against the resolved node is skipped. Validation keeps draft-07 semantics, under which siblings of a `$ref` constrain nothing.

Custom-template `json_schema` documents resolve `#/definitions/...` refs against their own definitions first, then against the BFF definitions (editor models such as `ImageModel`, `LinkSource`, `TextArea`). Refs under `#/definitions/partials/...` point at server-side template fragments and are treated as unconstrained.

**Never send real settings to migrate.** On live data it replaces content with demo placeholders; its only safe role is reporting a widget's actual version on empty settings.

## Write workspace and full-replace push

`content pull --out WORK` snapshots the full content into `WORK` plus a pristine `WORK.base.json` and `WORK.manifest.json` (`base_version_id`, sha256 of the base, source URL, counts, `bff_url` — the storefront address the pull was made for, `null` when none was given — and `schema_build_version` of that storefront's cached schema, `null` with a `schema_note` when there is none). Later workspace commands take the storefront address from `bff_url`; a flag or `KIT_BFF_BASE_URL` on another host is refused (it may be another store's schema — drop it, or pull again for the right address), and only a workspace without a recorded address takes them. A workspace with `bff_url: null` never falls back to a single cached schema, which may belong to another store. Editing commands (`page add/set/remove`, `section set/add/remove/move/status`, `theme set`) mutate `WORK` only, validate at edit time, and print a compact report. `content templates-sync --work WORK` sends one `GET /section-templates` (`GetSectionTemplates`) and adds every template the snapshot does not have yet to the working copy **and** the base snapshot alike, refreshing the manifest's `base_sha256` and leaving `base_version_id` alone; the write never carries templates (the server takes them from its own store), so this changes nothing the push sends and keeps gate 8 satisfied. A known template whose html, css, schema, script, title or alias differs on the server is listed under `templates_changed_on_server` and not replaced. `templates create --work WORK` does the same for the template it has just created. `content diff --work WORK` is a fully offline diff against the base; sections of an added page are reported as additions. `section add` / `section move` give the section a free `display_sequence` between its neighbours; with no gap left they renumber only the block between the header and footer slots, in steps of ten. The header keeps its number (1, or 2 behind an announcement bar); a footer below 9999 — a page numbered 1..N keeps it right after the last section — is first lifted to 9999 and the end of that page's layout, and the command report carries `footer_renumbered` (`section_id`, `before`, `after`). The sequence is stored per page copy, and the storefront renders the header area, the content and the footer in that order whatever the numbers, so the lift changes nothing visible. Neither slot can be moved, and nothing is renumbered before the header (refused there: the block has to fit below the header's number). Without `--position` a section is added right before the footer slot.

### Page model

There is **no page endpoint**: pages travel only inside the full-replace body, exactly as the B2B cabinet writes them. A page carries `id` (UUID), `title`, `pattern`, `exact`, optional `alias`, `variant_type`, `status`, optional `meta` (`seo_title`/`seo_h1`/`seo_description`), optional `static_context`, and `layout`. Page rules checked locally by `kitlib/pages.py` — server refusals mirrored, plus the client's own rules, each named as such:

* **Pattern** is normalized like the server does (leading `/` added, one trailing `/` stripped). The pattern of an aliased page belongs to the server, and backend versions treat it differently: an older one refuses the write unless the pattern equals its own table entry (and refuses `~` routes on every alias but `categoryAndCollection`), a newer one writes the alias's canonical pattern whatever is sent and returns it on read. Both accept the pattern they gave on read, so the client sends it unchanged and refuses edits to it; a new aliased page takes the canonical pattern of the client's table. A custom page gets exactly one pattern (`~`-joined routes exist only on system pages: `categoryAndCollection`, `accountProfile`) and must not take a canonical pattern whole: the server looks the pattern up in its table and makes the page that system page — silently when the store has none yet (`/account/refunds`: the refunds page is not created with a store), with 400 for the whole write when it already has one (`/cart`, created with every store: two pages on one pattern). Patterns are unique across pages, except several `productCard` / `categoryAndCollection` variants sharing their canonical pattern.
* **Routes a system page already serves** (client rule): a custom page may not take a single `~` route of a system page this store has (`/account`, `/account/profile` of `accountProfile`) or an address such a page's `:param` route matches (`/catalog/sale` under `/catalog/:categorySlug`, `/blog/news` under `/blog/:blogEntrySlug`). A parameter matches Latin letters, digits, `_`, `-` and `%`; the category and collection slugs also `/`. The server stores such a page, but the storefront tries pages in no fixed order and opens the first match, so either page answers at that address. Addresses with Cyrillic letters, spaces or `. ! ' +` in that place are free. When the store does not have the system page, the address is free today and is accepted with a `warnings` entry: the page may be added later. Adding a system page whose route matches a stored custom page warns the same way.
* **Custom page address characters**: the whole pattern must match `(/[а-яА-ЯёЁa-zA-Z0-9 ._!'+-]+)+` — letters, digits, spaces and `. _ ! ' + -` in non-empty `/` segments, so no `:param`, `~`, `%` escapes, `?`, `#`. The address is checked as the server normalizes it, without trimming whitespace. A newer server rule applies this to **every** custom page of each write, not only to changed ones. Locally, an address the edit introduces is a gate error. A stored address that breaks the rule is a `warnings` entry in the push plan, not a gate: a backend with the rule answers the write with 400 and writes nothing, one without it accepts the write, and the client cannot tell which one serves the store. The way out, if the push is refused, is `page set --pattern`; links to the old address stop working.
* **Alias** comes from the server's fixed catalog of 34 system aliases (an unknown one fails the whole write) and is immutable on an existing page. `cartPreview` (`/cart-preview`), `unsubscribe` (`/unsubscribe`), `emailConfirmed` (`/email-confirmed`) and `emailConfirmationFailed` (`/email-confirmation-failed`) are pages the server keeps without the store header and footer; `page add` does not copy them there. `page add --alias` creates a missing system page for any alias except `emailConfirmed` and `emailConfirmationFailed`: nothing on the platform adds those pages to a store, and their content widgets are not in the storefront widget schema, so the page could only be empty. A store that has them reads and edits them like any page. `page add --alias` places the system page's content widget(s) at the server's own sequence (a copy of the server's default page table: `accountRefunds` → `YandexKit.AccountRefunds`, `productCard` → `YandexKit.ProductDetails`, `categoryAndCollection` and `search` → `YandexKit.ProductsListing`, the text pages → `YandexKit.RichText` headed by the page title, `main` and `404` → none), each built as `schema widget --skeleton` plus the version from `schema widget-version` — so it reads the cached BFF schema and calls `migrate` with empty settings; a widget that cannot be built is reported in `warnings` and the page stays empty there. `--copy-layout-from default` on a new `productCard` / `categoryAndCollection` variant copies the default variant's layout instead: ordinary sections as new ids, composite copies (header, footer, shared blocks) as child copies of the same id. The manifest records each new id with the section it came from (`copied_sections`, dropped once a published push makes the copies base sections), and the settings gate judges a copy against that section: drift of today's schema the default template already carries — common on live stores — does not block the write, and the report lists it as `inherited_drift` (`section_id`, `widget`, the first `findings`). At most one `default` variant per alias; extra pages per alias exist only for `productCard` and `categoryAndCollection` (product/collection page templates, assigned in the B2B cabinet — the assignment is not part of constructor content).
* **`variant_type`** and **`exact`** are derived — the server recomputes the variant on write and derives `exact` from the pattern on read; the client refuses hand-set values that contradict the derivation.
* **`status`** is `published`/`hidden`; `hidden` is accepted only for custom pages (no alias) and the aliases `accountLoyalty`, `blog`, `blogEntry`, `catalog`, `discountLadder`, `favouriteProducts`, `giftCard`, `giftCardQuestions`, `loyaltyLanding`, `loyaltyOffer`, `subscription`. For any other alias the server refuses the whole write with 400; those pages are always published.
* **`meta`** (SEO) is allowed only on static pages (`exact: true`); the server keeps robots/social/twitter meta of an existing page and takes only the three SEO fields from the write. On `cart`, `cartPreview`, `search`, `favouriteProducts`, `unsubscribe`, `emailConfirmed`, `emailConfirmationFailed`, `accountProfile`, `accountOrders`, `accountNewsletters` and `accountRefunds` the storefront never reads them — it renders the store-wide template from the SEO settings. Meta set there is stored and has no visible effect; `page add` / `page set` and the push plan say so in `warnings`. On every other static page the title and description are read, but `seo_h1` is never printed, so an `seo_h1` the edit sets is a `warnings` entry too. The storefront's H1 comes from the sections, rendered header area first, then the content, then the footer: a page block whose heading outranks section titles (`ProductDetails`, `ProductsListing`, `CollectionsListing`, `Blog`, `BlogListing` with a title, `ShoppingCart`, the account blocks, `FavouriteProducts`, `GiftCard`, `DiscountLadder`, `ProductReviewsListing`) takes it when the page has one. The rank is page-wide: such a block without a heading of its own — `BlogListing` without a title, and `LoyaltyProgram`, which writes its title as an h2 — lifts it all the same, so no section title takes the H1 in the server HTML (`none_in_server_html`; the block is `raised_by`, and `after_hydration` names the section title the browser promotes once the scripts run). Without such a block the H1 goes to the first section title that has text and is not a link — `FeaturedProducts` (`titleText`, except on a `category` / `collection` source, where the title is a link), `FeaturedCollections` (`title`), `FeaturedBlogs`, `ImageWithText`, `RichText` (`titleText`), `Faq` (`title`), `EmailSubscription` (its own form title), and a `Mystique` template's `ya-kit-section-title` without `to`. `BannersCarousel` has no section title; its slide titles are h2. Custom markup that writes `<h1>` or `as="h1"` itself is outside that choice and prints one more H1. `page show` reports the result as `h1_hint`.
* A **default page with an alias can never be dropped** (400 for the whole transaction); a page missing from the body is deleted, and a page without an alias is deleted **silently**. A page that a menu item links to is not deleted at all: the server refuses the whole write with 400 («Страница "…" привязана к пункту меню. Для удаления страницы необходимо сначала убрать этот пункт в разделе "Меню"») and writes nothing. Which pages the menu links to is not readable through this API; the item is removed in the cabinet, then the same push is repeated — a menu edit does not change the content version. Menus are not versioned at all: the removed item is gone from the live storefront at once, and no content version or `--no-publish` write restores it.
* Removing an `alternative` `productCard` / `categoryAndCollection` page clears the assignments of products, categories and collections to it (an assignment points at the page variant, and the server clears it when the variant goes): they fall back to the default template. A reverted version, and the copy a `--no-publish` write re-activates, bring the page back without them. `page remove` reports `assignment_warning` and the push plan repeats it as a warning — for `--no-publish` with the note that the write is not a safe preview.
* Not checkable locally: a pattern colliding with an SEO **redirect** page — the server rejects that write with 400 and names the pattern; resolve it in the cabinet under Настройки → SEO → Редиректы.
* Not checkable locally either: the store's caps on the number of pages, on sections per page and on modules in one section (the entries of its `settings.modules`). They are store settings this client cannot read; a write over a cap, the no-publish one included, is refused with 400 «Превышено максимальное количество … Максимум — N» and nothing is written.

Page-level drift already present in the pulled data never blocks a push (same baseline principle as section settings); only pages the edit added or changed are validated. The address-character rule above reports stored addresses as plan warnings, because the server applies it to every page.

`content push --work WORK --commit-message M [--dry-run | --confirm] [--allow-page-removal] [--no-publish]` sends `PUT /constructor/content` (`UpdateConstructorContent`) with the body:

```json
{"pages": [...], "global_settings": {...}, "base_version_id": N, "commit_message": "M", "activate": false}
```

`activate` (optional, default `true`) is included only when `--no-publish` is passed. With `activate: false` the server, in one transaction, stores the body as a proposal version and re-activates a copy of the previously active content — the storefront never changes.

Pages are converted from the read shape by dropping `categories_count`, `collections_count`, and `product_cards_count`; everything else, including `instance_id` and the pattern of an aliased page, is carried through as read. The success response is compact: `{"version": {...}, "active_version_id": K, "pages_count": N, "sections_count": M}`; the client compares the counts against local expectations and warns loudly on divergence. Extra unknown response fields are tolerated — validators must never demand "no extra fields", because the contract grows (that is exactly how `active_version_id` arrived).

`active_version_id` is the version active after the write. With `activate: true` it equals `version.id`; with `activate: false` it is the server-made copy of the previous content. **An old server does not send it and silently publishes despite `activate: false`** — when `--no-publish` was requested and the response has no `active_version_id`, the client reports that the edit was published and the preview mode is unsupported, and exits `4`.

After every successful push the client rebases the workspace: the manifest's `base_version_id` moves to `active_version_id`. On a published write the base snapshot becomes the written working copy; on a no-publish write the base keeps its content (that is what stayed active) and only its version id moves, while the working copy keeps the proposal — so `content diff` still shows it and a follow-up publish push carries a fresh CAS base instead of hitting 409.

Local gates, all before any confirmation prompt, token load, or network access:

1. the workspace manifest exists and matches its base snapshot digest;
2. no base page is missing from the body — a page with an alias and `variant_type: default` can never be dropped (the server rejects the whole transaction with 400); other removals require `--allow-page-removal`;
3. no page alias changed;
4. every added or changed page passes the page model rules above (known alias, unique ids and patterns, an aliased page's pattern as read, reserved patterns and routes of the store's system pages, variant derivation, status subset, meta on static pages only);
5. every added or changed section's widget exists in the cached BFF schema, or is `YandexKit.Mystique` with a `template_id` found in the pulled catalog (settings that use an editor model such as `ImageModel` or `Palette`, which the template takes from the storefront schema, need that schema too: without it the gate names `--bff-url` and `schema fetch`); an added or rebound regular (`usual`) section never uses a header or footer template;
6. changed settings validate against their schema — but only errors introduced by the edit block; drift already present in the pulled data does not, including in a copy `page add --copy-layout-from default` made under a new id (judged against the section it came from);
7. composite copies of one section id carry identical widget, `template_id`, and settings on every page — the server stores those once per id, from the parent copy (status is per copy and may differ);
8. `section_templates` in the workspace are byte-identical to the base snapshot — the write transport does not carry templates, so a template edit could neither be written nor previewed; markup changes go through a new template plus a `template_id` rebind.
9. no section copy is `hidden` unless its widget allows it — including a copy that is already hidden in the pulled version: the server checks every section of a write, not only the edited ones, so such a copy fails the whole write with 400 until it is shown or removed.

Full-replace semantics (server side): a page missing from the body is not carried into the new version; custom pages without an alias are dropped silently; a missing page that a menu item links to fails the whole write with 400 instead; section templates are not transmitted — the server keeps the existing ones, and reading any version returns the current templates (a template edit affects every version and is not undone by reverting); a composite section is stored once per storefront and the parent copy's settings win.

`--dry-run` prints the gate-checked plan (diff summary, never the payload, plus `warnings` when there are any) and exits 0 offline. A confirmed push prints one JSON document on stdout, `{"plan": <plan>, "result": <response>}` — for `--no-publish` the result is the `proposal_stored_not_published` record, for exit `4` the published response; the loud messages, count mismatches and errors go to stderr, so `json.load` on stdout always works. The diff summary — in the plan and in `content diff` alike — covers pages as well as sections: `pages_added`, `pages_removed`, and `pages_changed`, one entry per kept page whose `title`, `pattern`, `status` or `meta` changes, each field as `{"before": …, "after": …}`. `warnings` collects what the push does not block: stored custom addresses a newer server rule refuses, SEO meta set on a page whose meta the storefront never reads, a custom address that a system page the store lacks would also serve (or the reverse, a new system page over a stored custom address), a section added or rebound onto a `YandexKit.AnnouncementBar` template, a custom page whose address changes (the old address stops opening), a removed product or collection template (its assignments are cleared), and a new custom page that nothing links to yet (no menu item, no link from a section). Unconfirmed push exits `3` offline. On 409 the client rereads content once, reports `version_conflict` with both versions, and exits `1` without retrying.

## Create a section template

`templates create --file PATH [--chrome-slot header|footer] [--work WORK] [--show-body] --confirm` sends one `POST /section-templates` (`CreateSectionTemplate`). Required non-empty strings: `title`, `html`, `css`, `json_schema` (a JSON string decoding to an object), `commit_message`. Optional: `script` (string, sent as `""` when absent — the API lists it as a required field) and `alias`. Unknown fields are rejected. `--dry-run` validates and prints a compact plan without token or network access: `operation`, `title`, `alias`, `html_bytes`, `css_bytes`, `json_schema_bytes`, `script_bytes`, `body_sha256` (sha256 of the body serialized with sorted keys), `schema_fields` (`path`, `type` or `$ref` name, `title`; refs into the template's own definitions followed, at most 120 entries, `schema_fields_truncated` beyond that), `script_warning` when `script` is not empty, and `chrome_slot` / `store_wide_warning` with `--chrome-slot`. `--show-body` adds the exact `body`. After a confirmed create stdout carries one JSON document, `{"plan": <the same plan>, "result": <created record>}`; the record comes without its source: `id`, `title`, `alias`, `json_schema_bytes`, `script_bytes`, and `version`. Creation does not attach the template to a page; attachment is `section add --widget YandexKit.Mystique --template-id` plus `content push`. Update and delete are unavailable.

`alias` is stored verbatim and checked by nothing server-side; an empty string is stored as a set, empty alias, not as none. What it does:

* Nothing for hiding: the server accepts `hidden` on every `YandexKit.Mystique` section whatever its template's alias (it stopped checking the alias for that).
* A template aliased `YandexKit.Header` / `YandexKit.Footer` is what the server treats as the store header or footer when the slot's section uses it. Pages the server adds later get that header and footer, and a page left without a footer gets the main page's footer back, the custom one included.
* The storefront places a custom section by its template's alias: `YandexKit.Header` and `YandexKit.AnnouncementBar` render in the header area above the page content, `YandexKit.Footer` in the footer area below it, anything else in the content. `section add --template-id` / `section set --template-id` onto an existing `YandexKit.AnnouncementBar` template (the cabinet makes them) are accepted with a warning in the report and in the push plan.
* The cabinet's «Заменить» list for a built-in section shows only templates whose alias names that widget.

The client therefore:

* drops `alias: ""` from the body, so the server stores none, as it does for templates made in the cabinet (older clients sent `""`);
* accepts the two chrome values only together with `--chrome-slot`. The flag itself sets the matching alias, so a regular section file needs no edit, and a chrome alias already in the file must match it. The plan then carries `chrome_slot` and a `store_wide_warning` to show the user before `--confirm`;
* refuses near-misses of the chrome values (`yandexkit.header`, stray spaces);
* refuses every other value as a policy of this skill, not as a server rule. An alias naming a native widget is the cabinet's «Заменить» feature, which this skill does not support (and `YandexKit.AnnouncementBar` would move the sections into the header area); any other string means nothing to the server or the storefront. Placing a chrome template into the slot means switching the slot section's widget to `YandexKit.Mystique` on every page copy: `section set --id SLOT --widget YandexKit.Mystique --template-id T --settings-file s.json` does that (the cabinet does it through «Заменить»), only for a template whose alias matches the slot, checking the settings against it; `--widget YandexKit.Header` / `YandexKit.Footer` switches back, stamping the widget version from migrate. Both report a `store_wide_warning`, the diff marks the slot with `widget_changed`, the plan repeats the warning, and the composite gate keeps every copy equal. Once the slot holds a custom template, `section set --template-id` only accepts templates with the same alias, and `section add` refuses chrome templates.

| Client command | Method and path | Operation ID | Contract |
|---|---|---|---|
| `media upload --file PATH --confirm` | `POST /files` | `UploadFile` | multipart `file`; returns `public_path` and normalized `url` |
| `media video-upload --file PATH --confirm` | `POST /videos` | `UploadVideo` | multipart `file`; returns opaque `video_id` |
| `media font-upload --file PATH --confirm` | `POST /files` | `UploadFile` | multipart `file` sent as `font/woff2`, `font/woff`, `font/ttf` or `font/otf`; the response must be `type: OTHER` (a generic file); prints `file_id`, `file_path` and `sources_fragment` `{fileId, filePath}` for `typography.fontFamily.custom.sources` |

Uploads read only a user-provided local file. Source URLs are rejected. The maximum size is 104857600 bytes. Images must be supported non-SVG/non-ICO `image/*`; videos support mp4, mov, webm, avi, and flv; fonts `.woff2`, `.woff`, `.ttf`, `.otf` (by extension; the content type is set explicitly). The server stores content that is not an Avatars-compatible image as a generic file with type `OTHER`; a font that comes back as anything else is refused, since a theme font source must be such a file.

## Authentication and contour selection

Token resolution order: `KIT_TOKEN`, `KIT_TOKEN_FILE`, `~/.yandex-kit-skills/kit_api.token`. Tokens are trimmed, must contain no whitespace, and are never printed. The BFF is unauthenticated; no token is ever sent to it.

Three ways to fill the token file, one validation rule (`yakit_` prefix, no whitespace) shared by all of them:

| Command | Input | Notes |
|---|---|---|
| `token save` | hidden terminal prompt, or stdin when piped | needs a TTY or a pipe; a pipe exposes the value to whatever produced it |
| `token web` | a form on a one-shot local page | the value goes browser → token file, never through the agent; needs the client and the browser on one machine |
| `token save` from stdin | the user sends the value in the conversation, as text or as a file | the hosted-session route when the environment settings are out of reach: it works everywhere, and the value stays in the conversation history — say so, then tell the user they can revoke the token afterwards |
| — | `KIT_TOKEN` / `KIT_TOKEN_FILE` set by the user | takes precedence over the file; `token web` says so on the page |

`token web` opens `http://127.0.0.1:<port>/?secret=<one-time>` (`--port 0` by default picks a free port) and makes no network call of any kind. Before binding anything it checks that the page could reach a browser on this host — SSH environment variables, container markers (`/.dockerenv`, `/run/.containerenv`, PID 1 cgroups), a Linux session without a display, or no registered browser — and refuses with exit `2` and instructions when the answer is no, because in a hosted session the printed link resolves to the *user's* machine, where nothing is listening. `--force` skips that check for a user who forwards the port themselves. Its guards: loopback bind, loopback peer **and** `Host` header (which is what refuses a DNS-rebinding page), a 256-bit URL secret compared in constant time and capped at 20 wrong attempts, request logging off, the token accepted only in a POST body, a page with `default-src 'none'` and no external resource, a body-size cap, one successful save then exit, and a `--timeout` deadline (default 300 s, max 3600). Exit `0` when a token was saved, `2` on timeout, refusal, or a port that cannot be bound. `--no-open` prints the URL without launching a browser.

## Failure behavior

| Exit | Meaning |
|---|---|
| `0` | success |
| `1` | HTTP/API or network failure (including 409 after the single reread); JSON error envelope on stderr |
| `2` | local validation/configuration failure, including failed push gates |
| `3` | mutation refused because confirmation is absent or the operation is unavailable |
| `4` | the write succeeded but the requested no-publish mode was not honored: the server ignored `activate: false` and **published the edit** (no `active_version_id` in the response). The change is live on the storefront |

HTTP 401/403 is reported without exposing the token. Responses are JSON-validated and fail closed on malformed required fields.
