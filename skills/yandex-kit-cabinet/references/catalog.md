# Каталог — категории, характеристики, продукты, товары, файлы, склады

Endpoint map for the catalog domain. Auth, base URL, tool flags, pagination and
global conventions live in [`api.md`](api.md). Mutating = POST/PUT/PATCH/DELETE
(all need `--confirm`).

## Domain conventions

- «Продукт» (`/v1/products`) groups variants; «товар» (`/v1/variants`) is the
  sellable unit with price/stocks/media. Media references file IDs from
  `kit.py upload`.
- Variant (товар) statuses: `PUBLISHED` | `HIDDEN` | `ARCHIVED`. Only an
  `ARCHIVED` variant can be deleted permanently.

## Правила поведения (не выражены в схеме)

Проверено по коду хендлеров; схему полей смотрите через
`kit.py describe <METHOD> <path>`.

- **Архив блокирует запись.** Архивные товары, характеристики и склады нельзя
  обновлять через `PATCH` — вернётся `400`. Сначала `unarchive`, потом правка.
- **`archive` / `unarchive` идемпотентны**: повторный вызов для уже архивного
  (или уже активного) объекта проходит успешно и ничего не меняет.
- **Продукт обязан лежать хотя бы в одной категории.** Последнюю категорию
  продукта, у которого есть неархивные товары, нельзя заархивировать без
  `archive_variants=true`. Передача архивной категории в продукт **не**
  разархивирует её автоматически.
- **`slug` генерируется сам** из названия у категорий и складов, если не
  передан, и обязан быть уникальным. Конфликт склада разрешается суффиксом.
- **`PATCH /v1/warehouses/{id}` не архивирует.** Для смены статуса есть только
  `archive` / `unarchive`.
- **Устаревшее поле.** В характеристиках товара используйте `values` (массив),
  а не `value` (строка): singular помечен deprecated и логируется на бэкенде.
  Спека при этом по-прежнему числит `value` обязательным — `kit.py validate` это
  знает и тело только с `values` пропускает, а `value` API заполнит сам. Элемент
  массива `characteristics`:
  `{"characteristic_id": "<id характеристики>", "values": ["Хлопок"]}`. Тело с
  одним `value` тоже пройдёт, но с предупреждением; без обоих — отказ.
- **`DELETE /v1/variants/{id}` необратим** и работает только для `ARCHIVED`.
- Размерная сетка ссылается на `file_id`, который должен быть заранее загружен
  через `POST /v1/files`.
- `per_page` ограничен сотней; `page` начинается с 1.

## Категории

| Метод | Путь | Описание |

| GET | `/v1/categories` | Получение списка категорий (обязателен `-q status=…`) |
| POST | `/v1/categories` | Создание новой категории |

У категории нет флага видимости: «убрать категорию с витрины» — это `archive`,

**SEO категории — есть:** `seo_title` и `seo_description` в
`PATCH /v1/categories/{id}`. Задайте их каждой категории: при пустых полях
витрина подставляет шаблон магазина с обещаниями вроде «Большой ассортимент»
(рецепт «SEO каталога пачкой» — в [`workflow.md`](workflow.md)).

**Через API у категории не задать** описание (у подборок оно есть —
`description` в `PATCH /v1/collections/{id}`) и альтернативный шаблон
страницы. Оба — только в кабинете, раздел «Товары». Пока шаблон не
назначен, вариант страницы категории, собранный в конструкторе витрины,
покупатель не увидит.

### Что значат поля характеристики

Схему печатает `kit.py describe POST /v1/characteristics`; здесь — что поля
делают с товаром и витриной.

- **`type` — сколько значений у одного товара.** `STRING` — одно строковое
  значение, `MULTIPLE_STRING` — несколько («Хлопок», «Лён»), `INT` — одно число.
  Два значения в `values` у `STRING` API отклонит: «Строковая характеристика не
  позволяет установить 2 значений». `STRING` меняется на `MULTIPLE_STRING`
  через `PATCH /v1/characteristics/{id}`, в том числе когда значения у товаров
  уже заполнены.
- **`select_mode` — как покупатель фильтрует, а не сколько значений у товара.**
  `MULTIPLE` — флажки с условием «или»; `SINGLE` — выбор одного значения;
  `RANGE` — два поля «от — до» для числа; `MULTIPLE_STRICT` — флажки с условием
  «и», для `MULTIPLE_STRING`. `RANGE` на витрине — два пустых поля без подсказки
  границ; при трёх–шести значениях понятнее `MULTIPLE`.
- **`unit` витрина не выводит** — ни в переключателе на карточке, ни в блоке
  «Характеристики», ни в фильтре: покупатель увидит голое «5». Единицу пишите в
  название («Вес одеяла, кг»), а если характеристика группирующая и её значения
  стоят в переключателе — прямо в значение («150 мл»), то есть делайте её
  `STRING`, а не `INT`.
- **Порядок значений `MULTIPLE_STRING` не сохраняется**: они хранятся по
  алфавиту, «Утро, Вечер» вернётся как «Вечер, Утро». Смысл в порядке не
  кодируйте — разнесите по отдельным характеристикам или перепишите значения.

Без единиц и с перепутанным порядком карточка выглядит недоделанной, поэтому
эти правила — не мелочь оформления.

### Характеристики и фильтры витрины

Новая характеристика сама в фильтры не попадает: во всех категориях она
создаётся выключенной как фильтр. Включить её фильтром категории или подборки,
задать порядок или скрыть можно только в кабинете — **Редактор сайта →
Фильтры**; ручек для этого в публичном API нет. После создания характеристик
назовите владельцу, какие из них включить и в каких категориях, — иначе
фильтры на витрине останутся пустыми.

### Цвета значений

`PATCH /v1/characteristics/colors` задаёт hex (`#RRGGBB`, `multicoloured` или
`transparent`) только тем значениям, которые уже есть в
`GET /v1/characteristics/colors`; создать цвет через API нельзя. В этот список
значение попадает, когда характеристика стала **группирующей** у продукта (см.
«[Продукт с несколькими товарами](#продукт-с-несколькими-товарами)») и в
кабинете для неё выбрано отображение цветом. Пустой список (`total_count: 0`)
значит, что `PATCH` ответит `404` «Цвет со значением … не найден». Так и
скажите владельцу, назвав оба условия, — не перебирайте другие написания
значения.

### Продукт с несколькими товарами

Продукт объединяет товары одной модели. Как они показываются, решают две
настройки продукта — `settings` в `PATCH /v1/products/{id}`:

- **группирующая характеристика** (`grouping_characteristic_ids`) — товары
  остаются на одной карточке, и на ней появляется переключатель: размер,
  объём, цвет;
- **разбивающая** (`splitting_characteristic_ids`) — продукт делится на
  отдельные карточки по значениям характеристики.

Пока у продукта нет группирующей характеристики, второй товар в него не
добавить: `POST /v1/variants` с его `product_id` ответит `400` «Укажите
группирующие характеристики», хотя `validate` тело пропустит — тело здесь
правильное, неправильный порядок шагов. Порядок:

1. Характеристика для переключателя есть (`list /v1/characteristics -q
   status=ACTIVE`) или создана (`POST /v1/characteristics`).
2. `PATCH /v1/products/{id}` с
   `{"settings": {"grouping_characteristic_ids": ["<id>"], "splitting_characteristic_ids": []}}`
   — оба массива обязательны, пустой тоже передаётся.
3. У каждого товара продукта, включая уже существующий, — своё значение этой
   характеристики (`characteristics` в `PATCH /v1/variants/{id}`): два товара с
   одним значением переключатель не различит.
4. `POST /v1/variants` с тем же `product_id` и своим значением.

Перенос товара в другой продукт (`PATCH /v1/variants/{id}` с новым
`product_id`) упирается в то же правило: группирующую характеристику
настраивают на **целевом** продукте до переноса. Получив этот `400`, клиент
сам печатает порядок шагов. Рецепт целиком — «Добавить вариант в существующий
продукт» в [`workflow.md`](workflow.md).

### Похожие карточки

`/v1/products/cards/{product_card_id}/similar` — источник полки «Похожие» / «С
этим покупают» на странице товара. В маленьком каталоге платформе не из чего
подобрать похожие самой, и полка выходит пустой или повторяет сам товар:
дайте каждой карточке 3–4 похожих (`similar/add`, `{"similar_card_ids": […]}`).
`product_card_id` — id карточки, а не товара и не продукта; он есть в ответе
`GET /v1/variants`.

Связь симметрична — так `similar/add` описан в спеке: добавив B к A, вы
добавили и A к B. Поэтому идите не по карточкам, а по группам, иначе у каждой
карточки станет больше похожих, чем вы планировали:

1. Разбейте каталог на группы по 4–5 действительно похожих карточек.
2. Внутри группы у каждой карточки добавляйте только те, что идут после неё:
   A — `[B, C, D]`, B — `[C, D]`, C — `[D]`. В группе из четырёх у каждой
   выйдет по 3 похожих, из пяти — по 4.
3. Перед вызовом прочитайте `GET …/similar` у карточки: прежние вызовы уже
   могли дать ей обратные связи.

### Чего с продуктом и карточкой через API не сделать

- **Удалить продукт** — ни `DELETE`, ни `archive` у `/v1/products` нет. Продукт
  без товаров на витрине не виден, но в кабинете остаётся. Переносите товары
  так, чтобы не плодить пустышки: сначала выберите целевой продукт и переносите
  в него, а не заводите новый под каждый товар.
- **Изменить адрес карточки.** Он формируется из названия первого товара при
  создании и через API не меняется — `slug` в `PATCH /v1/variants/{id}` нет.
  Название первого товара выбирайте осознанно: без размера и цвета, если
  вариантов будет несколько.
- **Назначить товару альтернативный шаблон страницы** — только в кабинете,
  раздел «Товары». Пока шаблон не назначен, вариант страницы, собранный в
  конструкторе витрины, покупатель не увидит.

`system_type` — это перечисление в пути, а не свободная строка. Допустимые

любое другое написание даст `404`, а не ошибку валидации. Это рабочая связка
для интеграций с товароучёткой и маркетплейсами: сначала прочитайте
`GET …/external_ids`, чтобы менять или снимать существующую привязку осознанно,
а не вслепую.

### Массовые обновления цен и остатков

| Метод | Путь | Описание |
|---|---|---|
| POST | `/v1/variants/prices/bulk_update` | Массовое обновление цен (до 5000 элементов за запрос) |
| POST | `/v1/variants/stocks/bulk_update` | Массовое обновление остатков (до 5000 пар товар+склад) |

Для регулярной синхронизации цен и остатков используйте именно эти ручки, а не
`PATCH /v1/variants/{id}` по одному товару. Пара «товар + склад» в одном запросе
на остатки не может повторяться.

### Документы товара

| Метод | Путь | Описание |
|---|---|---|
| GET | `/v1/variants/{id}/attachments` | Документы товара (инструкции, сертификаты, паспорта) |
| POST | `/v1/variants/{id}/attachments` | Прикрепление документа по ID ранее загруженного файла |
| PATCH | `/v1/variants/{id}/attachments/{file_id}` | Обновление названия и/или порядка документа |
| DELETE | `/v1/variants/{id}/attachments/{file_id}` | Открепление документа от товара |

Сначала загрузите файл (`kit.py upload`), затем прикрепите его по `file_id`.
`DELETE` открепляет локально — сам файл остаётся и может использоваться другими
товарами.
