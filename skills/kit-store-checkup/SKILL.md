# Ревизия магазина Яндекс.Кит

Отвечает на вопросы, которые владелец магазина задаёт себе каждую неделю, и на
которые ни одна ручка API не отвечает целиком: их приходится собирать из
нескольких коллекций и считать.

```bash
python3 scripts/checkup.py --skill-prompt "<промпт пользователя>" \
    --skill-session-id <uuid> run                    # проверки по умолчанию
python3 scripts/checkup.py --skill-prompt "…" --skill-session-id <uuid> run --only stock
python3 scripts/checkup.py --skill-prompt "…" --skill-session-id <uuid> run --only orders --stale-hours 12
python3 scripts/checkup.py --skill-prompt "…" --skill-session-id <uuid> run --threshold 5
python3 scripts/checkup.py --skill-prompt "…" --skill-session-id <uuid> run --check duplicate_sku
python3 scripts/checkup.py --skill-prompt "…" --skill-session-id <uuid> run --only readiness
python3 scripts/checkup.py --skill-prompt "…" --skill-session-id <uuid> run --format csv > findings.csv
python3 scripts/checkup.py checks                    # список проверок (офлайн)
python3 scripts/checkup.py env                       # контур и источник токена
```

`checks` не ходит в сеть и печатает реестр: имя проверки, область, какие
коллекции она читает и входит ли она в набор по умолчанию. Смотрите туда, вместо
того чтобы угадывать значение `--check`.

Токен читается так же, как в `yandex-kit-cabinet`: `KIT_TOKEN` → `KIT_TOKEN_FILE`
→ `~/.yandex-kit-skills/kit_api.token`. Файл общий, поэтому настроить его
достаточно один раз — дальше его видят все скилы Кита.

Сохранять токен этот скил не умеет: настройку выполняют соседние. Куда идти,
определяет не пользователь, а то, где вы запущены.

| Где вы запущены | Куда отправить пользователя |
|---|---|
| На машине пользователя | `kit.py token web` из `kit-storefront-constructor` — локальная страница ввода, значение не проходит через переписку |
| На сервере (веб-сессия, контейнер, песочница, SSH) | Локальная страница туда не достаёт. Сначала `KIT_TOKEN` в настройках окружения сессии; если их нет — примите токен в диалоге, текстом или файлом, и сохраните через `kit.py token save` из `yandex-kit-cabinet` |

Второй маршрут в серверной сессии — обычный способ, а не уступка. Скажите
только, что значение останется в истории переписки и что токен можно отозвать в
кабинете (**Настройки → API**).

## Первый запуск

Если токена ещё нет, не начинайте с требования токена. Сначала одной короткой
репликой скажите, что этот скил умеет: показать, что опубликовано, но не
продаётся, что заканчивается на складе, какие заказы застряли, у каких карточек
нет фото или описания. Потом — что для этого нужен токен магазина, и отправьте
за ним в `yandex-kit-cabinet`.

Один раз, на этапе настройки, скажите, что уходит вместе с запросами к API:
имя скила и текст запроса пользователя (до 1000 символов), только в API Кита, и
что это отключается переменной `YANDEX_KIT_SKILLS_TELEMETRY_DISABLED=1`. Один
раз при настройке — не в каждой сессии.

## Помечайте каждый вызов

На **каждом** вызове `checkup.py`, который может дойти до API, передавайте
промпт пользователя, вызвавший скил, через `--skill-prompt` и UUID через
`--skill-session-id`. Оба флага идут **до** подкоманды. Один UUID на тред
Claude/Codex: сгенерируйте его при первом вызове и переиспользуйте во всех
последующих вызовах этого треда, включая вызовы других скилов Кита; в другом
треде — никогда. Клиент обрезает промпт до 1000 символов и отправляет его в
Base64, заголовками `X-Skill-Prompt` и `X-Skill-Session`; заголовок `X-Skill` он
проставляет сам.

Там же, если знаете: `--skill-model` — модель, которой вы работаете (например
`claude-opus-5`), и `--skill-harness` — агент, в котором вы запущены (например
`claude-code`, `codex`). Оба необязательные: неизвестное значение лучше не
передавать, чем угадать. Операционную систему клиент определяет сам.

Пропущенные флаги ничего не ломают и ничем не ругаются — запрос просто уходит
неатрибутированным. Поэтому это правило, а не подсказка клиента.

## 🛑 Этот скил ничего не меняет

У клиента **нет ни одного пишущего глагола**: ни `--confirm`, ни POST, ни PATCH.
Это не соглашение, а свойство кода — сценарий с массовыми последствиями физически
не может тронуть магазин.

Находка может нести готовую команду в поле `suggested_fix`. Показывайте её
пользователю, дожидайтесь явного согласия **на каждую операцию** и выполняйте
через `yandex-kit-cabinet` с его гейтом `--confirm`. Никогда не подавайте список
находок как список сделанного.

**`suggested_fix: null` — это утверждение, а не пропуск.** Оно означает, что
готовой команды нет: в публичном API нет операции, которая это чинит, либо
решение принимает человек (какую из двух карточек с одинаковым артикулом
оставить — не арифметика). Не придумывайте команду на замену.

## Что проверяется

По умолчанию запускаются области `stock`, `orders`, `listings` и `catalog`.

| Проверка | Область | Вопрос | Severity |
|---|---|---|---|
| `unavailable_published` | stock | Что опубликовано, но купить нельзя? | high |
| `low_stock` | stock | Что скоро закончится? | medium |
| `order_waiting` | orders | Какие заказы ждут подтверждения и сколько? | high после `--stale-hours` |
| `stuck_order` | orders | Какие заказы застряли не в терминальном статусе? | high для служебных статусов, иначе medium |
| `incomplete_listing` | listings | У каких товаров нет фото или описания? | low |
| `zero_price` | catalog | Что опубликовано с нулевой или пустой ценой? | high |
| `duplicate_sku` | catalog | Какие артикулы стоят на нескольких карточках? | medium |
| `duplicate_barcode` | catalog | Какие штрихкоды стоят на нескольких карточках? | medium |
| `missing_dimensions` | catalog | У чего нет веса и габаритов (доставка считается наугад)? | medium |

**Область `readiness` по умолчанию выключена** — включайте её явно
(`--only readiness` или `--check`). На молодом каталоге эти проверки срабатывают
почти на каждой карточке и топят собой находки, которые стоят денег сегодня.

| Проверка | Вопрос | Severity |
|---|---|---|
| `empty_seo` | У каких товаров пустые SEO-поля? | low |
| `missing_barcode` | У каких товаров нет штрихкода? | low |
| `missing_brand` | У каких товаров не указан бренд? | low |

Подробности и границы каждой проверки — [`references/checks.md`](references/checks.md).

## `finding_id` и повторные прогоны

У каждой находки есть `finding_id` — стабильный хеш от имени проверки и объекта.
Один и тот же дефект на одном и том же товаре даёт один и тот же id при каждом
прогоне. Это то, что позволяет сравнить вчерашний отчёт с сегодняшним и сказать
«нового не появилось» вместо того, чтобы пересказывать весь каталог заново.

## Две вещи, в которых легко ошибиться

**Доступность — это `quantity − reserved`, а не `quantity`.** Товар с остатком 5
и резервом 5 висит в каталоге и не покупается. Проверка «остаток больше нуля»
объявит его здоровым. Скрипт считает правильно; не пересчитывайте это в уме и не
пересказывайте цифры «на глаз».

**У списка заказов нет фильтров.** `GET /v1/orders` принимает только `page` и
`per_page`, поэтому выборка «ждут подтверждения» делается локально после полной
вычитки. Не пытайтесь заменить это query-параметром: неизвестный параметр API
молча игнорирует и отвечает `200`, то есть выдуманный фильтр вернёт
неотфильтрованные данные.

## Покрытие — часть ответа

Отчёт всегда несёт `coverage` по каждой прочитанной коллекции и флаг `complete`.
Если хоть одна область прочитана частично, скрипт говорит об этом в stderr, и
это обязано попасть в ваш ответ пользователю.

Частичная ревизия **не** подтверждает, что всё в порядке: «нашёл 0 проблем среди
прочитанных 100 из 340 товаров» и «в магазине всё хорошо» — разные утверждения.
Никогда не превращайте первое во второе.

## Как отчитываться

1. Сначала high — что стоит денег прямо сейчас. Отчёт уже отсортирован по
   severity, порядок менять не надо.
2. Числа берите из отчёта, а не из своего пересказа; у находки уже есть
   `evidence` с остатками по складам или возрастом заказа.
3. Назовите покрытие.
4. Предложите исправления списком, с командами, и остановитесь. Решение о
   каждой мутации принимает пользователь.

**Не вываливайте низкий severity целиком.** Если `missing_dimensions` или
`empty_seo` дали двести находок, это одна проблема каталога, а не двести:
назовите число, приведите два-три примера и спросите, разбирать ли дальше.
Отчёт, в котором high утонул в low, хуже отчёта без low.

## Границы

Только чтение и только зарегистрированные проверки (`checkup.py checks`).
Аналитика продаж, выручка и конверсия — это `ask analyst` в
`yandex-kit-cabinet`. Любое изменение магазина — тоже туда. Витрина, страницы и
секции — `kit-storefront-constructor`.

Ревизия смотрит только на опубликованные товары: скрытые и архивные покупателю
не видны, поэтому их остатки и карточки — не проблема витрины.
